# Services Delta — Safqa API · Contracts (change-20260805-171001)

### SVC-CONTRACTS-01 · ContractsDataService [domain, internal, Contracts]
- Status: done (delta)
- `renderContractHtml` — `workspaceBranding` input gains `defaultFont?: string` and `colorRoles?: { primary; secondary?; accent?; surface?; text? }`. New helper `buildGoogleFontLinkHtml(fontFamily)` maps the resolved font name to its Google Fonts `<link>` markup (`Cairo` / `Tajawal` / `Amiri`, each with the same weight/style set already used elsewhere in the codebase for that family; `Amiri` uses `ital,wght@0,400;0,700;1,400;1,700` per the user-supplied `<link>`). New vars added to the token map: `document_font_link`, `document_font` (CSS `font-family` value, e.g. `'Amiri', serif`), `brand_primary` / `brand_secondary` / `brand_accent` / `brand_surface` / `brand_text` (from `colorRoles`, with Roya-default hex fallbacks when the workspace has no palette — same fallback triad already used by DNA branding: `#47B5E6` / `#114261` / `#2C8DBE`), and `contract_total` (grand-total figure, reusing the same computation as `buildFinancialTableRows`'s totals, exposed as a small new exported helper `computeContractTotal(services, proposal)` so both stay in sync).
- `createContractFromProposal` — `workspaceBranding` object passed into `renderContractHtml` now also includes `defaultFont: getString(publicSettings.defaultFont)` and `colorRoles: (publicSettings.colorRoles as ... ) || undefined` (both already present on `getPublicSettings()`'s return — no new fetch).
- No change to persisted contract document shape, no change to `overrides` mechanism, no change to existing tokens' values/behavior.
- Post-verify amendment: `{{contract_number}}` no longer renders the raw internal `contractDocId` — new `generateContractNumber(seed)` helper derives a deterministic 8-character uppercase alphanumeric display code (e.g. `QK7XZV3M`) from it via a mixed FNV-1a + multiplicative hash. Same contract always shows the same code; no new persisted field, no migration.

### SVC-CONTRACTS-02 · ContractPdfService [domain, internal, Contracts]
- Status: done (delta)
- `renderContractPdf` now also reads `colorRoles` off the already-fetched `getPublicSettings(workspaceId)` result (no new call) and passes `colorRoles?.primary` into `buildFooterTemplate` for a branded accent color on the page-number badge.
- `buildFooterTemplate(contact, primaryColor?)` — page number span restyled larger/bolder (reads as a deliberate watermark-style page marker rather than plain small footer text) and tinted with `primaryColor` when available (fallback: existing gray `#555`). Contact info (email/phone/address) styling unchanged.
- `buildHeaderTemplate` unchanged (still text-only running workspace-name title, per the prior pack's duplicate-logo fix).
- The workspace-name diagonal watermark itself is **not** produced by this service — it's static CSS/markup inside the contract's own HTML body (see `contract-templates.md` delta), which Chromium repeats on every printed content page via `position: fixed` with no per-page JS needed. This service's only watermark-adjacent responsibility is the footer page-number styling above.
- `fetchLogoAsDataUri` / `stripConflictingPageMargin` unchanged — the cover page's logo reuses the same `{{workspace_logo}}` token/URL, so the existing base64-inlining swap (`contractHtml.split(logoUrl).join(logoDataUri)`) already covers the cover without any code change.
- **Post-verify amendment — two-pass render for true cover bleed.** `renderContractPdf` now renders the cover and the content pages as two separate `PdfRenderService.renderHtmlToPdf` calls and merges the results with the new `pdf-lib` dependency:
  - New `withBodyClass(html, className)` toggles a `<body>` class (`pdf-cover-pass` / `pdf-content-pass`) on the same rendered HTML string so the template's print CSS (see `contract-templates.md` delta) shows only the cover or only the content for that pass — no template duplication.
  - Cover pass: `margin: 0` on all sides, `displayHeaderFooter: false` (no header/footer band on the cover).
  - Content pass: unchanged `18/20/16mm` margins + existing header/footer templates.
  - New `mergePdfBuffers(buffers)` (via `pdf-lib`'s `PDFDocument.load`/`copyPages`) concatenates the two single-purpose PDFs (cover first) into the one buffer returned/uploaded as before. Reason: Chromium's print-to-PDF clips content to the page's margin box regardless of CSS (negative margins, overflow, etc.) — a single `page.pdf({ margin })` call cannot give one page a `0` margin while the rest keep the normal margin, so the split was necessary at the PDF-generation layer, not just in CSS.
  - Side effect (verified, expected): the footer's "Page N / Total" now counts only the content pages, not the cover — matches how a cover isn't normally page 1 of a document's pagination.

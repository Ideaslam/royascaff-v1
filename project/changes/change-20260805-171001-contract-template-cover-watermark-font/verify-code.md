## Notes / Deviations
- **Cover is not true edge-to-edge bleed.** *(Superseded — resolved in Post-verify fix round 3 via a two-pass render + PDF merge; kept here for history.)* Puppeteer's `page.pdf({ margin })` applies uniformly to every page; the prior pack's post-verify fix explicitly removed all `@page { margin }` CSS (even `:first`-scoped) because Chromium gives such a declaration priority over the JS `margin` option and had silently broken every page's margin previously. Fighting that again with negative-margin bleed tricks would reintroduce exactly the class of bug that caused two rounds of visual complaints last time. Instead, the cover fills the entire printable content box (`min-height: 259mm`, matching the A4 content height under the standard `18/20mm` margins) with the branded gradient — visually a full "page" of color, just inset by the same margin frame as every other page. Functionally satisfies "full-bleed branded cover page" (AC 3) without the regression risk.
- **In-body letterhead removed, not duplicated.** The change-request's Description section originally said the cover would sit "in addition to" the existing letterhead block. During blueprinting this was revised (see `contract-templates.md` SVC-CONTRACT-TEMPLATES-01 delta, already drafted and confirmed before implementation) to fold the letterhead into the cover instead, replacing it with a slim one-line recap on the article page — avoiding a second near-identical logo/title block right after the cover, which would look redundant and echoes the "two logos" bug fixed in the prior pack.
- **`contract_total` lives in the "Content" token group**, not "Design / Branding" — it's a financial-summary figure (same value as the financial table's totals), not a design/branding token; grouped with `services`/`financial_table` instead. (Blueprint doc updated to match.)
- Live PDF review used a standalone sample-data render (same Puppeteer options as `ContractPdfService`) rather than a full create-contract round trip through the running app, since no seeded workspace/contract fixture was readily available in this session. Recommend the user also download a real contract PDF once to confirm end-to-end before merging.

## Post-verify fix round 2 (bug found by user, before PASS)
User hit `{"error":"defaultFont must be one of the following values: Cairo, Tajawal"}` when saving `Amiri` from Workspace Settings — **this is a real gap in acceptance criterion 1** (`defaultFont` select should persist `Amiri` via the existing PATCH flow), missed during implementation:
- Root cause: `PatchSettingsDto.defaultFont` had a hardcoded `@IsIn(['Cairo', 'Tajawal'])` class-validator decorator in `settings.dto.ts` that was never updated when `Amiri` was added to `settings-schema.ts`/`config-seed-data.js` — two independent, un-synced sources of truth for the same allowed-values list. `currency` had the identical pattern (`@IsIn(['SAR', 'USD'])`).
- Fix (user asked to "make it dynamic" so future seed-only font additions never need a code change again):
  - New `validateSelectFieldValues(patch, schema)` in `settings-schema.ts` — generic, schema-driven: for every `select`-type field with a static `options` list (skips `optionsRef` fields like `model`, which resolve from a different config doc), checks the patched value is one of the field's *currently loaded* `options` (DB `config/settingsSchema` when seeded, else `FALLBACK_SETTINGS_SCHEMA`) and throws a `400` with a message built from that live list.
  - `SettingsDataService.patchSettings` calls it right after `loadSettingsSchema()` (same call already used elsewhere in that method), before persisting.
  - Removed the now-redundant hardcoded `@IsIn(['Cairo','Tajawal'])`/`@IsIn(['SAR','USD'])` from `settings.dto.ts` (both fields keep `@IsString()` for basic type-shape validation only) — the DTO no longer duplicates a list that can drift from the schema/seed.
- Net effect: adding/removing a font (or currency) option going forward only ever requires editing `settings-schema.ts` + `config-seed-data.js` (already the documented single source for the field's `options`) — no DTO edit, no redeploy-and-forget risk of the two lists diverging again.
- Verified: `tsc --noEmit` clean; `dto-validation.spec.ts` (existing `PatchSettingsDto` test) still passes unchanged.

## Post-verify fix round 3 (cover redesign, before PASS)
User asked to fix the cover: (1) no margin — true edge-to-edge bleed, (2) bigger title, (3) a single solid color instead of the gradient, with no swirl/lines — same overall style/organization as the reference image, just flattened to one color:
- **Solid color, no gradient/pattern**: `.cover` background is now `background: var(--brand-secondary)` only (the darker of the two brand roles, closer to the reference's dark hero look) — removed `background-image: linear-gradient(...)`, and deleted the `.cover-wash` (dark gradient overlay) and `.cover-swirl` (repeating-radial-gradient decoration) elements/CSS entirely, per "without lines and without gradient."
- **Bigger title**: `.cover-title` font-size `30px → 46px` (`max-width` widened `85% → 92%` so the larger text still wraps naturally at 2 lines).
- **True edge-to-edge bleed — required a PDF-generation-layer fix, not just CSS**: confirmed empirically (rendered + screenshotted) that a CSS negative-margin/overflow trick does **not** work — Chromium's print-to-PDF clips page content to the margin box regardless of what the CSS does, so the cover kept showing the same white margin frame as every other page. Since `page.pdf({ margin })` applies one uniform margin to the whole document, no single-pass render can give page 1 a `0` margin while every other page keeps `18/20/16mm`. Fixed by splitting `ContractPdfService.renderContractPdf` into **two Puppeteer render passes merged into one PDF**:
  - Added `pdf-lib` (new prod dependency) — `mergePdfBuffers()` loads N PDF buffers and concatenates their pages into one output document.
  - Added `withBodyClass(html, className)` — toggles a `<body>` class on the already-rendered contract HTML string (no template duplication).
  - Template gained two small print-only rules gated on that body class: `body.pdf-cover-pass` hides `.contract-page`/`.watermark` and lets `.cover` claim the full page; `body.pdf-content-pass` hides `.cover`. (The pre-existing `.cover { position:relative; z-index:10 }` watermark-hiding trick is left in place as a no-op safety net for any plain single-document print/preview path that doesn't go through the two-pass split.)
  - Pass 1 renders only the cover at `margin: 0mm` all sides, `displayHeaderFooter: false` (no header/footer band on the cover — an improvement over the previous single-pass version, which couldn't avoid showing them there).
  - Pass 2 renders only the content pages at the existing `18/20/16mm` margins with the existing header/footer templates, unchanged.
  - The two buffers are merged with the cover first. Side effect (verified, and considered correct): the footer's "Page N / Total" now counts only the content pages (matches how a cover isn't normally "page 1" of a document's pagination) — e.g. cover is the PDF's physical page 1, and the first article page shows footer "Page 1 / 7" while being physical page 2.
  - `@page { size: A4 }` (no margin) was left as-is in the template; `preferCSSPageSize` only affects page *size*, not the JS `margin` option, so the two passes' different margins aren't affected by it.
- Verified: `tsc --noEmit` clean; `npx eslint --fix` on the touched file (pure formatting, no logic change); re-rendered the sample contract through the exact same two-pass-render + merge logic `ContractPdfService` now uses and screenshotted the output — cover paints solid navy edge-to-edge on all 4 sides with no header/footer band and a visibly larger title; watermark + brand-tinted page numbers still render correctly starting on the first content page; re-ran `npm run seed:contract-templates` to push the updated template HTML into `contract_templates`.
